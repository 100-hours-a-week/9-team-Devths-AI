## ADR-026: Gunicorn + Uvicorn 서버 구조

### 📋 메타데이터

| 항목 | 내용 |
|------|------|
| **상태** | ✅ 승인됨 (Accepted) |
| **작성일** | 2026-01-12 |
| **결정자** | AI팀 |
| **관련 기능** | FastAPI 서버, 프로덕션 배포, 성능 최적화 |

---

### 🎯 컨텍스트 (Context)

**프로덕션 환경에서 FastAPI 서버의 성능과 안정성**을 보장해야 합니다.

**문제점:**
- Uvicorn 단독 사용 시 단일 프로세스 (CPU 코어 활용 부족)
- 동기/비동기 요청 혼재 시 성능 저하
- 추론 서버 부하로 인한 전체 서버 영향

**요구사항:**
- 멀티 프로세스 지원 (CPU 코어 활용)
- 동기/비동기 요청 처리 최적화
- 추론 서버 분리 (부하 격리)

---

### 🔍 선택지 분석 (Options)

#### Option 1: Uvicorn 단독

```bash
# 단일 프로세스
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

```
┌─────────────────────────────────────────────────────────────────┐
│  Uvicorn 단독                                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [Client] → [Uvicorn (단일 프로세스)] → [FastAPI]               │
│                                                                 │
│  문제점:                                                         │
│  - CPU 코어 1개만 사용                                           │
│  - 동시 요청 처리 제한                                           │
│  - 추론 작업 시 전체 서버 블로킹                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

| 장점 | 단점 |
|------|------|
| 간단한 설정 | CPU 코어 1개만 사용 |
| 개발 환경 적합 | 동시 처리 제한 |
| | 프로덕션 부적합 |

```bash
# 멀티 프로세스 (CPU 코어 활용)
```

```
│                                                                 │
│  장점:                                                           │

│  - Worker 재시작 (장애 복구) ✅                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

| 장점 | 단점 |
|------|------|

```
│      - 데이터 처리                                               │
│      - API 라우팅                                                │
│      ↓                                                          │
│  [HTTP Request] → [추론 서버] (별도 프로세스)                    │
│                                                                 │

│      ├─ Sync Worker 1 (동기)                                    │
│      ├─ Sync Worker 2 (동기)                                    │
│      └─ Sync Worker 3 (동기)                                    │
│      ↓                                                          │

│  - API 서버: 비동기 (I/O 최적화) ✅                              │

│  - 부하 격리 (추론 작업이 API 서버 영향 안 줌) ✅                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

| 장점 | 단점 |
|------|------|
| **부하 격리** | 복잡도 증가 |
| **동기/비동기 최적화** | 네트워크 오버헤드 |
| **독립 스케일링** | 관리 포인트 증가 |
| **프로덕션 최적** | |

---

### ✅ 결정 (Decision)

**단계적 접근: Uvicorn → Gunicorn+Uvicorn → 추론 서버 분리**

| 버전 | 구조 | 이유 |
|------|------|------|
| **V1~V2** | Uvicorn 단독 | 개발 환경, 간단 |
| **V3** | **Gunicorn + Uvicorn** | 프로덕션, 멀티 프로세스 |
| **V4** | **Gunicorn + Uvicorn + 추론 서버** | 부하 격리, 최적화 |

---

### 📝 근거 (Rationale)

#### 1. Gunicorn + Uvicorn의 필요성

**Uvicorn 단독의 문제:**
```python
# 단일 프로세스 (CPU 코어 1개만 사용)
uvicorn app.main:app --host 0.0.0.0 --port 8000

# 동시 요청 처리:
# - 요청 1: 처리 중...
# - 요청 2: 대기 중... (블로킹)
# - 요청 3: 대기 중... (블로킹)
```

**Gunicorn + Uvicorn의 장점:**
```bash
# 멀티 프로세스 (CPU 코어 4개 활용)
gunicorn app.main:app \
  --workers 4 \
  --worker-class uvicorn.workers.UvicornWorker \
  --bind 0.0.0.0:8000

# 동시 요청 처리:
# - Worker 1: 요청 1 처리 중...
# - Worker 2: 요청 2 처리 중...
# - Worker 3: 요청 3 처리 중...
# - Worker 4: 요청 4 처리 중...
```

**성능 향상:**
- ✅ CPU 코어 활용률: 25% → 100%
- ✅ 동시 처리량: 4배 증가
- ✅ 응답 시간: 50% 감소

---

#### 2. 추론 서버 분리의 필요성

**문제: 추론 작업이 API 서버에 영향**
```python
# API 서버에서 직접 추론
@app.post("/ai/analyze")
async def analyze(file: UploadFile):
    # 1. 텍스트 추출 (빠름)
    text = extract_text(file)
    
    # 2. LLM 추론 (느림, 1~3초)
    result = llm.invoke(text)  # ← 이 동안 Worker 블로킹!
    
    return result

# 문제:
# - LLM 추론 중 Worker가 다른 요청 처리 못함
# - 추론 작업이 많으면 전체 API 서버 느려짐
```

**해결: 추론 서버 분리**
```python
# API 서버 (비동기)
@app.post("/ai/analyze")
async def analyze(file: UploadFile):
    # 1. 텍스트 추출 (빠름)
    text = extract_text(file)
    
    # 2. 추론 서버로 요청 (비동기)
    async with httpx.AsyncClient() as client:
        result = await client.post(
            "http://inference-server:8001/infer",
            json={"text": text}
        )
    
    return result.json()

# 추론 서버 (동기)
@inference_app.post("/infer")
def infer(request: InferRequest):
    # LLM 추론 (동기, CPU 최적화)
    result = llm.invoke(request.text)
    return result
```

**장점:**
- ✅ API 서버: 비동기 I/O 최적화
- ✅ 추론 서버: 동기 CPU 최적화
- ✅ 부하 격리 (추론 작업이 API 서버 영향 안 줌)

---

#### 3. Worker 수 계산

**권장 Worker 수:**
```python
# CPU 바운드 작업 (추론 서버)
workers = (CPU 코어 수 * 2) + 1

# 예: 4 코어
workers = (4 * 2) + 1 = 9

# I/O 바운드 작업 (API 서버)
workers = CPU 코어 수 * 2

# 예: 4 코어
workers = 4 * 2 = 8
```

**프로젝트 적용:**
```bash
# API 서버 (비동기, I/O 바운드)
gunicorn app.main:app \
  --workers 8 \
  --worker-class uvicorn.workers.UvicornWorker \
  --bind 0.0.0.0:8000

# 추론 서버 (동기, CPU 바운드)
gunicorn inference.main:app \
  --workers 9 \
  --worker-class sync \
  --bind 0.0.0.0:8001
```

**2. API 서버 (api_server/main.py):**
```python
from fastapi import FastAPI
import httpx

app = FastAPI()

INFERENCE_SERVER_URL = "http://inference-server:8001"

@app.post("/ai/analyze")
async def analyze(file: UploadFile):
    """분석 API (비동기)"""
    
    # 1. 텍스트 추출
    text = extract_text(file)
    
    # 2. 추론 서버로 요청 (비동기)
    async with httpx.AsyncClient() as client:
        response = await client.post(
            f"{INFERENCE_SERVER_URL}/infer/analyze",
            json={"text": text}
        )
    
    return response.json()
```

**3. 추론 서버 (inference_server/main.py):**
```python
from fastapi import FastAPI
from langchain_google_genai import ChatGoogleGenerativeAI

app = FastAPI()

# LLM 초기화 (서버 시작 시 한 번만)
llm = ChatGoogleGenerativeAI(model="gemini-3-flash")

@app.post("/infer/analyze")
def infer_analyze(request: AnalyzeRequest):
    """추론 API (동기)"""
    
    # LLM 추론 (동기, CPU 최적화)
    result = llm.invoke(request.text)
    
    return {"result": result}
```

### 🎯 컨텍스트 (Context)

**AI의 일관된 페르소나**를 통해 사용자 경험을 향상시켜야 합니다.

**문제점:**
- AI 응답이 매번 다른 톤/스타일
- 사용자가 AI의 역할을 명확히 인지 못함
- 면접 모드와 일반 채팅의 구분 모호

**요구사항:**
- 일관된 AI 페르소나 (톤, 스타일, 역할)
- 상황별 페르소나 변경 (일반 채팅 vs 면접 모드)
- 사용자 친화적 경험

---

### 🔍 선택지 분석 (Options)

#### Option 1: 페르소나 없음 (기본)

```python
# 페르소나 없이 직접 질문
prompt = f"이력서를 분석해주세요: {resume_text}"
result = llm.invoke(prompt)
```

| 장점 | 단점 |
|------|------|
| 구현 간단 | 일관성 없음 |
| 프롬프트 짧음 | 사용자 경험 저하 |
| | AI 역할 모호 |

---

#### Option 2: 단일 페르소나 ⭐

```python
# 단일 페르소나 (모든 상황에서 동일)
PERSONA = """
당신은 '커리어 코치 AI'입니다.
- 이름: 커리어봇
- 역할: 취업 준비생의 커리어 코치
- 톤: 친근하고 전문적
- 스타일: 격려하고 구체적인 조언 제공
"""

prompt = f"{PERSONA}\n\n이력서를 분석해주세요: {resume_text}"
result = llm.invoke(prompt)
```

| 장점 | 단점 |
|------|------|
| 일관된 톤/스타일 | 상황별 유연성 부족 |
| 구현 간단 | 면접 모드에 부적합 |
| 사용자 친화적 | |

```python
from enum import Enum
from langchain_google_genai import ChatGoogleGenerativeAI

class PersonaType(Enum):
    CAREER_COACH = "career_coach"
    INTERVIEWER = "interviewer"
    CALENDAR_ASSISTANT = "calendar_assistant"

class PersonaManager:
    """페르소나 관리 클래스"""
    
    PERSONAS = {
        PersonaType.CAREER_COACH: CAREER_COACH_PERSONA,
        PersonaType.INTERVIEWER: INTERVIEWER_PERSONA,
        PersonaType.CALENDAR_ASSISTANT: CALENDAR_ASSISTANT_PERSONA,
    }
    
    @classmethod
    def get_persona(cls, persona_type: PersonaType) -> str:
        """페르소나 가져오기"""
        return cls.PERSONAS.get(persona_type, cls.PERSONAS[PersonaType.CAREER_COACH])
    
    @classmethod
    def create_prompt(cls, persona_type: PersonaType, user_message: str) -> str:
        """페르소나 + 사용자 메시지로 프롬프트 생성"""
        persona = cls.get_persona(persona_type)
        return f"{persona}\n\n사용자 메시지: {user_message}"

# 사용 예시
llm = ChatGoogleGenerativeAI(model="gemini-3-flash")

# 1. 이력서 분석 (커리어 코치)

    PersonaType.CAREER_COACH,
    "이력서 분석해줘"
)

)

# 3. 일정 관리 (캘린더 어시스턴트)

    "내일 오후 2시에 면접 일정 추가해줘"
)
result = llm.invoke(prompt)
```

## ADR-028: API 통합 전략 - 텍스트 추출 API 통합

### 📋 메타데이터

| 항목 | 내용 |
|------|------|
| **상태** | ✅ 승인됨 (Accepted) |
| **작성일** | 2026-01-13 |
| **결정자** | AI팀 |
| **관련 기능** | 텍스트 추출, 임베딩, VectorDB, API 설계 |

---

### 🎯 컨텍스트 (Context)

**API 개수를 줄이고 책임 분리를 명확히**해야 합니다.

**문제점:**
- API 1 (`/ai/ocr/extract`): 파일 → OCR → 임베딩
- API 2 (`/ai/file/embed`): 텍스트 → 임베딩
- 두 API가 비슷한 기능 (임베딩 저장)을 수행
- VectorDB 정보를 백엔드에 반환하지만 백엔드는 사용하지 않음

**요구사항:**
- API 개수 감소 (5개 → 4개)
- 파일과 텍스트 입력을 하나의 API로 처리
- VectorDB 접근 방식 명확화 (AI 서버만 접근)
- 백엔드는 추출된 텍스트만 받아서 MongoDB에 저장

---

### 🔍 선택지 분석 (Options)

#### Option 1: 현재 구조 유지 (2개 API)

```
API 1: /ai/ocr/extract      → 파일 → OCR → 임베딩 → VectorDB
API 2: /ai/file/embed       → 텍스트 → 임베딩 → VectorDB
```

| 장점 | 단점 |
|------|------|
| 명확한 역할 분리 | API 개수 많음 |
| 구현 간단 | 중복 로직 (임베딩) |
| | VectorDB 정보 불필요하게 반환 |

---

#### Option 2: API 통합 (1개 API) ⭐

```
API 1: /ai/text/extract    → 파일 또는 텍스트 → 추출/임베딩 → VectorDB
                            → 백엔드에는 텍스트만 반환
```

| 장점 | 단점 |
|------|------|
| **API 개수 감소** | Request 검증 복잡 |
| **중복 로직 제거** | file_url/text 중 하나 필수 |
| **VectorDB 정보 제거** | |
| **책임 분리 명확** | |

### ✅ 결정 (Decision)

**Option 2: API 통합 (1개 API) 채택**

```
변경 전 (v2.0):
- API 1: /ai/ocr/extract     (파일 → OCR → 임베딩)
- API 2: /ai/file/embed      (텍스트 → 임베딩)

변경 후 (v3.0):
- API 1: /ai/text/extract    (파일/텍스트 → 추출/임베딩)
```

- ✅ 백엔드는 추출된 텍스트만 받음

```python
from pydantic import BaseModel, validator
from typing import Optional

class TextExtractRequest(BaseModel):
    type: Literal["resume", "portfolio", "job_posting"]
    user_id: str
    document_id: str
    file_url: Optional[HttpUrl] = None
    file_type: Optional[Literal["pdf", "image"]] = None

    @validator('text', always=True)

        return v
```

## ADR-029: LangChain PydanticOutputParser 사용

### 📋 메타데이터

| 항목 | 내용 |
|------|------|
| **상태** | ✅ 승인됨 (Accepted) |

| **결정자** | AI팀 |
| **관련 기능** | LLM 출력 구조화, 타입 안정성, API 응답 |

---

### 🎯 컨텍스트 (Context)

**LLM 출력을 구조화된 JSON으로 자동 변환**해야 합니다.

**명확한 용어 정리:**
- ✅ **Pydantic**: 파이썬 데이터 검증 라이브러리 (사용함)
- ❌ **Pydantic AI**: LLM 프레임워크 (사용하지 않음, ADR-019 참조)
- ✅ **LangChain PydanticOutputParser**: LangChain의 도구 (사용함)

**문제점:**
- LLM 출력을 수동으로 JSON 파싱
- 타입 검증이 약함
- 에러 처리 복잡

**요구사항:**
- LLM 출력 자동 JSON 변환
- Pydantic 모델로 타입 검증
- 코드 간결화

---

### 🔍 선택지 분석 (Options)

#### Option 1: 수동 JSON 파싱

```python
from langchain_google_genai import ChatGoogleGenerativeAI
import json

llm = ChatGoogleGenerativeAI(model="gemini-2.0-flash")
response = llm.invoke("이력서를 분석해주세요")
result = json.loads(response.content)  # ❌ 수동 파싱
```

| 장점 | 단점 |

## ADR-030: VectorDB 선택 (ChromaDB)

### 📋 메타데이터

| 항목 | 내용 |

### 🎯 컨텍스트 (Context)

**RAG (Retrieval-Augmented Generation) 구현을 위한 VectorDB 선택**이 필요합니다.

**요구사항:**
- 임베딩 벡터 저장 (768차원, Gemini/BERT)
- 유사도 검색 (코사인 유사도)
- 메타데이터 필터링 (user_id, document_type 등)
- LangChain 연동
- 로컬 실행 가능 (초기 비용 절감)

**데이터 규모:**
- V1/V2: 1,000-10,000 벡터
- V3: 10,000-100,000 벡터
- V4+: 100,000+ 벡터

### 🔍 선택지 분석 (Options)

#### Option 1: ChromaDB ⭐ (선택)

**장점:**
- ✅ 로컬 실행 가능 (SQLite 기반)
- ✅ LangChain 네이티브 지원
- ✅ Python API 간단
- ✅ 메타데이터 필터링 우수
- ✅ 무료 (오픈소스)
- ✅ 개발 속도 빠름

**단점:**
- ⚠️ 대규모 데이터 (1M+) 성능 제한
- ⚠️ 분산 처리 미지원
- ⚠️ GPU 가속 없음

**비용:**
- 로컬: $0
- 클라우드 (Chroma Cloud): $0.10/1M 쿼리

**성능:**
- 검색 속도: ~100ms (10K 벡터)
- 저장 용량: 10K 벡터 = ~100MB

**코드 예시:**

### 🔄 마이그레이션 전략 (V4+)

**ChromaDB → Milvus 마이그레이션 (100만 벡터 초과 시)**

```python
# scripts/migrate_to_milvus.py

from pymilvus import connections, Collection
import chromadb

async def migrate_to_milvus():
    """ChromaDB → Milvus 마이그레이션"""
    
    # 1. ChromaDB 데이터 조회
    chroma_client = chromadb.PersistentClient(path="./chroma_db")
    collection = chroma_client.get_collection("resumes")
    
    data = collection.get(include=["embeddings", "metadatas", "documents"])
    
    # 2. Milvus 연결
    connections.connect(host="localhost", port="19530")
    
    # 3. Milvus Collection 생성
    from pymilvus import FieldSchema, CollectionSchema, DataType
    
    fields = [
        FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
        FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=768),
        FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=65535),
        FieldSchema(name="user_id", dtype=DataType.VARCHAR, max_length=100),
    ]
    
    schema = CollectionSchema(fields)
    milvus_collection = Collection("resumes", schema)
    
    # 4. 데이터 삽입
    milvus_collection.insert([
        data["ids"],
        data["embeddings"],
        data["documents"],
        [m["user_id"] for m in data["metadatas"]]
    ])
    
    # 5. 인덱스 생성
    milvus_collection.create_index(
        field_name="embedding",
        index_params={"index_type": "IVF_FLAT", "metric_type": "L2", "params": {"nlist": 128}}
    )
    
    print("✅ 마이그레이션 완료!")
```
