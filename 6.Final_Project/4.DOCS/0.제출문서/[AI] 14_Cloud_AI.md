## 1. 개요

### 1.1. 용어 정리

| 용어 | 설명 | 트리거 | 응답 시간 |
|------|------|--------|----------|
| **실시간 (Sync)** | 요청 즉시 응답 | 사용자 요청 | 즉시 |
| **비동기 (Async)** | 요청 후 뒷단에서 처리 | 사용자 요청 | 대기 가능 |
| **배치 (Batch)** | 모아서 한꺼번에 처리 | 스케줄 (Cron) | 느려도 됨 |
| **서버리스** | 요청 시에만 서버 가동 | - | 인프라 방식 |

> 💡 **핵심**: 실시간/비동기/배치 = **처리 방식**, 서버리스 = **인프라 방식**

### 1.2. 버전별 처리 방식 전략

> 🎯 **최종 목표**: 사용자 데이터 축적 → 배치 처리 → 개인화 추천

| 버전 | 데이터 처리 | 처리 방식 | 설명 |
|------|------------|----------|------|
| **V1** | LLM만 (저장 X) | 실시간 | 단순 응답, 데이터 축적 없음 |
| **V2** | VectorDB (채팅방별) | 실시간 + **비동기** | 사용자 요청 → 뒷단에서 임베딩 저장 |
| **V3** | 전체 사용자 데이터 | 실시간 + 비동기 + **배치** | 스케줄로 공통 패턴 추출 |
| **V4** | 익명 데이터 공유 | 배치 고도화 | 사용자 맞춤 추천 시스템 |

```
V1: [요청] ─── 실시간 ───→ [응답]

V2: [요청] ─── 실시간 ───→ [응답]
              │
              └── 비동기 ───→ [VectorDB 저장] (채팅방별 개인화)

V3: [요청] ─── 실시간 ───→ [응답]
              │
              ├── 비동기 ───→ [VectorDB 저장] (개인화)
              │
    [Cron] ─── 배치 ───→ [전체 데이터 패턴 추출] → [추천용 VectorDB]
                                                      │
                                                      └──→ 맞춤 추천 (면접 질문 패턴, 합격자 이력서 등)
```

#### 배치 처리로 가능해지는 기능

| 기능 | V2 (개인화) | V3/V4 (배치 + 추천) |
|------|------------|-------------------|
| **면접** | 내 피드백 기반 질문 | + 유사 지원자 질문 패턴 추천 |
| **이력서** | 내 이력서 분석 | + 합격자 이력서 패턴 추천 |
| **매칭도** | 개인 점수 | + 비슷한 합격자 비교 분석 |

### 1.3. 현재 프로젝트 구조

| 항목 | 현재 사용 |
|------|----------|
| **LLM** | Gemini 3 Flash/Pro (GCP) |
| **Framework** | FastAPI + LangChain + LangGraph |
| **VectorDB** | ChromaDB (Self-hosted, RunPod) |
| **OCR** | Gemini Vision + CLOVA OCR (V2) |
| **캐시** | Redis |
| **인프라** | Docker → K8s or Cloud Run (계획) |

## 2. 클라우드 제공사별 AI 서비스

### 2.1. AWS (Amazon Web Services)

#### 🧠 머신러닝 & AI 플랫폼

| 서비스 | 용도 |
|--------|------|
| **Amazon SageMaker** | ML 모델 구축/학습/배포 전체 워크플로우 (AutoML, MLOps 포함) |

#### 📊 AI 서비스 (API 형태)

| 서비스 | 용도 |
|--------|------|

## 6. 배치 처리 vs 실시간 처리

> 💡 **핵심 질문**: 서버를 항상 띄워둘 것인가? 요청 시에만 처리할 것인가? 주기적으로 배치할 것인가?

### 6.1. 처리 방식 비교

| 처리 방식 | 설명 | 장점 | 단점 | 적합한 경우 |
|----------|------|------|------|------------|
| **실시간 (Always-on)** | 서버 상시 가동 | 즉시 응답, 낮은 레이턴시 | 비용 높음 | 사용자 대화, 면접 |
| **서버리스 (On-demand)** | 요청 시에만 서버 가동 | 비용 효율, 자동 스케일링 | 콜드 스타트 | 간헐적 호출 |
| **배치 (Batch)** | 주기적으로 모아서 처리 | 비용 최저, 효율적 | 지연 발생 | 임베딩, 분석 보고서 |

### 6.2. 기능별 처리 방식 결정

```
┌─────────────────────────────────────────────────────────────────────────────┐
│   기능별 처리 방식 결정 가이드                                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   [사용자 응답 시간 중요?]                                                    │
│        │                                                                    │
│        ├── Yes (즉시 응답 필요) ────────────────┐                            │
│        │                                       │                            │
│        │     [호출 빈도 높음?]                   │                            │
│        │        │                              │                            │
│        │        ├── Yes ─── 실시간 (Always-on)  │                            │

│        │        │                              │                            │

│                │                              │                            │

│                           예: OCR, 마스킹     │                            │
│                                               │                            │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 6.3. 프로젝트 기능별 처리 방식

| 기능 | 응답 시간 | 호출 빈도 | 권장 처리 방식 | 인프라 |
|------|:--------:|:--------:|:-------------:|--------|
| **채팅 (RAG)** | ⚡ 즉시 | 높음 | 실시간 | 상시 서버 |
| **면접 질문/답변** | ⚡ 즉시 | 높음 | 실시간 | 상시 서버 |
| **면접 리포트** | 🔄 약간 대기 | 낮음 | 서버리스/비동기 | Cloud Run |
| **분석 + 매칭도** | 🔄 약간 대기 | 중간 | 실시간 (스트리밍) | 상시 서버 |
| **이력서 임베딩** | ⏰ 지연 허용 | 낮음 | **배치 or 비동기** | 비동기 워커 |
| **OCR 추출** | ⏰ 지연 허용 | 낮음 | **비동기** | 비동기 워커 |
| **마스킹 (YOLO)** | ⏰ 지연 허용 | 낮음 | **비동기** | 비동기 워커 |
| **캘린더 파싱** | 🔄 즉시 | 낮음 | 실시간 or 서버리스 | FastAPI or Cloud Run |

### 6.4. 처리 방식별 인프라 설계

#### 실시간 (Always-on)
```
[사용자] → [FastAPI 서버 (상시 가동)] → [Gemini API]
                     │
                     └── Kubernetes / Docker Compose
```

#### 서버리스 (On-demand)
```
[사용자] → [API Gateway] → [Lambda/Cloud Run] → [Gemini API]
                                    │
                                    └── 요청 시에만 가동, 자동 스케일링
```

#### 비동기 (Async Worker)
```
[사용자] → [FastAPI] → [Redis Queue] → [Celery Worker] → [처리 완료]
                             │                   │
                             └── task_id 즉시 반환   └── 백그라운드 처리
```

#### 배치 (Batch)
```
[스케줄러 (Cron)] → [Batch Job] → [대량 처리] → [VectorDB 저장]
                          │
                          └── 야간/주기적 실행
```

### 6.5. 버전별 처리 전략

| 버전 | 전략 | 설명 |
|------|------|------|
| **V1** | 모두 실시간 | 단순화, 빠른 개발 |
| **V2** | 실시간 + 비동기 분리 | OCR, 임베딩을 비동기로 분리 |
| **V3** | 실시간 + 비동기 + 서버리스 | 호출 빈도 낮은 기능 서버리스 전환 |

### 6.6. 결정 요약

| 처리 방식 | 적용 기능 | 인프라 |
|----------|----------|--------|
| **실시간** | 채팅, 면접 Q&A, 분석 | FastAPI (상시) |
| **비동기** | OCR, 임베딩, 마스킹 | Celery + Redis |

### 7.3. 하이브리드 스케일링 전략 (V3+) ⭐

> 📌 **ADR-041 참고**: RunPod + Lambda 하이브리드 스케일링

#### 트래픽 패턴 분석

**문제점:**
- RunPod 단독 사용 시 피크 타임 대비 과도한 리소스 할당 필요
- 평시에는 30% 리소스 유휴 상태 → 비용 낭비

**해결책: 하이브리드 스케일링**

```
┌─────────────────────────────────────────────────────────────┐
│  하이브리드 스케일링 (RunPod + Lambda)                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [사용자 요청]                                              │
│      ↓                                                      │
│  [API Gateway / ALB] ← 로드 밸런서                          │
│      ├─ 라우팅 규칙                                         │
│      ├─ 헬스 체크                                           │
│      └─ 트래픽 분산                                         │
│      ↓                                                      │
│  ┌──────────────────┬──────────────────┐                   │
│  │                  │                  │                   │
│  │  [RunPod 서버]   │  [Lambda 함수]   │                   │
│  │  (베이스 라인)   │  (버스트)        │                   │
│  │                  │                  │                   │
│  │  평시 부하 70%   │  피크 부하 30%   │                   │
│  │  ├─ GPU 서버     │  ├─ 서버리스     │                   │
│  │  ├─ 항상 ON      │  ├─ 피크만 ON    │                   │
│  │  └─ $350/월      │  └─ $30/월       │                   │
│  │                  │                  │                   │
│  └──────────────────┴──────────────────┘                   │
│      ↓                      ↓                              │
│  [AI 모델 추론]                                             │

└─────────────────────────────────────────────────────────────┘
```

#### 라우팅 전략

```python
# routing-logic.py
def route_request(request):
    """스마트 라우팅 - RunPod vs Lambda"""
    
    # 1. RunPod 서버 상태 확인
    runpod_cpu = get_runpod_cpu_usage()
    runpod_healthy = check_runpod_health()
    
    # 2. 라우팅 결정
    if runpod_healthy and runpod_cpu < 70:
        # RunPod 여유 있음 → RunPod 사용
        return route_to_runpod(request)
    else:
        # RunPod 부하 높음 → Lambda 사용
        return route_to_lambda(request)
```
