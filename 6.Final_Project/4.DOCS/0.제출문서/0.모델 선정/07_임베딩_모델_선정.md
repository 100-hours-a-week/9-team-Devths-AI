## 1. 개요

### 목적
RAG(Retrieval-Augmented Generation)에서 사용할 임베딩 모델 선정

### 임베딩의 역할
- 텍스트를 벡터로 변환 (Semantic Search)
- VectorDB에 저장 (ChromaDB)
- 유사도 검색으로 관련 문서 검색

---

## 2. 요구사항

| 요구사항 | 목표 | 우선순위 |
|---------|------|---------|
| **한국어 성능** | Cosine Similarity 0.8+ | 높음 |
| **임베딩 차원** | 512~1024 차원 | 중간 |
| **처리 속도** | 문장당 50ms 이내 | 중간 |
| **비용** | 월 $10 이하 | 중간 |

### RAG 기반 선정 기준

본 프로젝트는 **RAG(Retrieval-Augmented Generation)** 기반이므로, 일반적인 임베딩 모델 선정 기준과 다릅니다.

#### RAG 사용 시 vs 미사용 시 비교

| 기준 | RAG 사용 시 (본 프로젝트) | RAG 미사용 시 |
|------|---------------------------|---------------|
| **핵심 지표** | Retrieval 성능 (검색 정확도) | 문장 유사도 정확도 |
| **유사도 타입** | 비대칭 (짧은 쿼리 ↔ 긴 문서) | 대칭 (문장 A ↔ 문장 B) |
| **task_type 지원** | 필수 (query/document 구분) | 선택 |
| **문서 길이 처리** | 긴 chunk 처리 필수 | 짧은 문장 위주 |
| **차원 수** | 768+ 권장 | 256~512로 충분 |

#### RAG용 임베딩 특징

```python
# RAG용 (비대칭 검색) - Gemini Embedding
query_embedding = embed("이력서 분석해줘", task_type="retrieval_query")
doc_embedding = embed(resume_chunk, task_type="retrieval_document")

# 일반 유사도 비교 (대칭) - ko-sbert 등
sent1_embedding = embed("오늘 날씨 좋다")
sent2_embedding = embed("날씨가 화창하네")
```

#### Gemini Embedding task_type 옵션

| task_type | 용도 | 본 프로젝트 사용 |
|-----------|------|-----------------|
| `retrieval_query` | RAG 검색 쿼리 | ✅ 사용 |
| `retrieval_document` | RAG 문서 인덱싱 | ✅ 사용 |
| `semantic_similarity` | 일반 유사도 비교 | - |
| `classification` | 분류 | - |
| `clustering` | 클러스터링 | - |

> **결론**: RAG 기반 서비스에서는 `retrieval` 성능이 핵심이므로, task_type을 지원하고 비대칭 검색에 최적화된 모델이 필요합니다.

## 3. 후보 모델 비교

### 3.1 Gemini Embedding ✅ 선정

**모델명**: `gemini-embedding-001`

**장점**:
- ✅ 높은 정확도 (768차원)
- ✅ 다국어 지원 (한국어 포함)
- ✅ 즉시 사용 가능 (API)
- ✅ 매우 저렴한 비용
- ✅ 자동 스케일링
- ✅ **task_type 지원** (query/document 구분)
- ✅ **MRL 지원** (768/1536/3072 차원 선택 가능)

**단점**:
- ❌ 인터넷 연결 필수
- ❌ 커스터마이징 불가

**비용**: $0.00001/1K tokens (거의 무료)

---

### 3.2 ko-sbert-multitask ❌ 미선정

**모델명**: `jhgan/ko-sbert-multitask`

**장점**:
- ✅ 한국어 특화 모델
- ✅ 로컬 실행 가능 (무료)
- ✅ 파인튜닝 가능
- ✅ 대칭 유사도 비교에 우수
- ✅ **속도 빠름** (98ms)
- ✅ **GAP 최대** (0.4111) - rule-based 검색에 강함

**단점**:
- ❌ 모델 로딩 메모리 필요 (~1GB)
- ❌ 서버 리소스 필요
- ❌ **task_type 미지원** (query/document 구분 불가)
- ❌ **비대칭 검색 최적화 안됨** (RAG에 부적합)

**비용**: $0 (서버 비용만)

**미선정 이유**:
```
ko-sbert는 문장 간 "대칭 유사도" 비교에 최적화된 모델입니다.
예: "오늘 날씨 좋다" ↔ "날씨가 화창하네" (문장 vs 문장)

본 프로젝트는 RAG 기반으로 "비대칭 검색"이 필요합니다.
예: "이력서 분석해줘" (짧은 쿼리) ↔ "3년 경력 백엔드 개발자..." (긴 문서)

ko-sbert는 task_type 구분이 없어 쿼리와 문서를 동일하게 처리하므로
RAG 검색 정확도가 떨어집니다.

→ RAG 미사용 시에는 ko-sbert가 좋은 선택
→ RAG 사용 시에는 Gemini Embedding이 적합
```

---

### 3.3 OpenAI text-embedding-3-small

**장점**:
- ✅ 높은 정확도 (1536차원)
- ✅ 한국어 성능 우수

**단점**:
- ❌ Gemini보다 2배 비쌈

**비용**: $0.00002/1K tokens

---

### 3.4 BGE-M3 (BAAI) ❌ 미선정

**장점**:
- ✅ 무료 (오픈소스)
- ✅ 다국어 지원

**단점**:
- ❌ GPU 권장
- ❌ 모델 크기 큼
- ❌ **느림** (372ms)
- ❌ **Gap 애매** (0.3289)
- ❌ 비유사 문장 점수가 너무 높음

**미선정 이유**: "만능 모델"이지만 RAG 특화는 아님. 연구/멀티태스크 실험용 정도.

## 4. 성능 벤치마크

### 4.1 종합 비교표 (실측)

| 모델 | 차원 | 타입 | 비용 | task_type | RAG Gap | 유사도 정확도 | 평균 속도(ms) |
|------|------|------|------|-----------|---------|---------------|---------------|
| **Gemini Embedding** | 768 | API | $0.00001/1K tok | ✅ O | 0.2044 | 0.9408 | 208.8 |
| ko-sbert-multitask | 768 | 로컬 | 무료 (로컬) | ❌ X | 0.4111 | 0.7739 | 98.2 |
| BGE-M3 | 1024 | 로컬 | 무료 (로컬) | ❌ X | 0.3289 | 0.7947 | 372.8 |

### 4.2 대칭 유사도 비교 (문장 ↔ 문장)

| 모델 | 유사 문장 평균 | 비유사 문장 평균 | 구분 Gap |
|------|----------------|------------------|----------|
| ko-sbert-multitask | 0.7739 | 0.0877 | **0.6862** |
| BGE-M3 | 0.7947 | 0.4382 | 0.3564 |
| **Gemini Embedding** | **0.9408** | 0.7029 | 0.2379 |

### 4.3 RAG 비대칭 검색 성능 비교 (쿼리 ↔ 문서)

| 모델 | 평균 관련 유사도 | 평균 비관련 유사도 | 평균 Gap | 평균 속도(ms) | task_type 지원 |
|------|------------------|---------------------|----------|---------------|----------------|
| ko-sbert-multitask | 0.5663 | 0.1552 | **0.4111** | 98.2 | ❌ |
| BGE-M3 | 0.6092 | 0.2803 | 0.3289 | 372.8 | ❌ |
| **Gemini Embedding** | **0.7635** | 0.5591 | 0.2044 | 208.8 | **✅** |

> **💡 Gap이 클수록 관련 문서와 비관련 문서를 잘 구분합니다.**
> **RAG에서는 Gap이 핵심 지표입니다.**

### 4.4 Gap 수치의 함정

**task_type 미지원 모델의 "Gap"은 착시일 가능성**

| 모델 타입 | 설명 |
|----------|------|
| **ko-sbert / BGE-M3** | 대칭 임베딩(S ↔ S) 기반. 쿼리와 문서를 같은 문장처럼 취급 |
| **Gemini** | 비대칭 임베딩 (Query ↔ Doc). 실제 검색 구조를 전제로 학습됨 |

**Gemini의 특성:**
- 비관련 문서 점수도 높게 나옴
- 대신 **랭킹이 안정적**
- 실서비스에선 **Top-K 품질이 더 좋음**

**결론:**
- Gap 수치만 보면 ko-sbert 승
- **RAG 현실 반영력은 Gemini 승**

## 5. 최종 선정

### 한 줄 결론

| 목적 | 추천 모델 |
|------|-----------|
| **실제 RAG 서비스 품질 최우선** | 👉 **Gemini Embedding** |
| 로컬 / 비용 0 / 빠른 응답 | 👉 ko-sbert-multitask |
| 범용 멀티링구얼·연구용 | 👉 BGE-M3 (비추천) |

### 선정 모델: Gemini Embedding

| 항목 | 내용 |
|------|------|
| **모델명** | gemini-embedding-001 |
| **차원** | 768 (MRL 지원: 768/1536/3072 선택 가능) |
| **비용** | $0.00001/1K tokens |
| **선정 근거** | RAG 비대칭 검색 최적화, task_type 지원, 한국어 성능 우수, 비용 거의 무료 |

### Gemini가 RAG에 제일 좋은 이유

1. **task_type 지원** (Query / Document)
2. **MRL (차원 조절 가능)**
3. **API 비용 거의 없음**
4. **운영 시 튜닝 포인트 많음**

### 💡 추천 세팅

```
벡터 DB 검색 → Top 20~50
LLM reranker 또는 Cross-Encoder 붙이기
```

### ko-sbert 미선정 요약

| 비교 항목 | Gemini Embedding | ko-sbert |
|----------|------------------|----------|
| **RAG 적합성** | ✅ 비대칭 검색 최적화 | ❌ 대칭 유사도용 |
| **task_type 지원** | ✅ query/document 구분 | ❌ 미지원 |
| **한국어 성능** | 0.94 (유사도) | 0.77 (유사도) |
| **운영 편의성** | ✅ API (서버 부담 없음) | ❌ 로컬 모델 (~1GB) |

> ko-sbert는 로컬 무료 실행이 가능하지만, RAG 기반 서비스에서는 비대칭 검색 성능이 중요하므로 Gemini Embedding 선정

### 비용 분석

```
월간 예상 사용량:
- 이력서 임베딩: 500건/월 × 500 tokens = 250K tokens
- 채용공고 임베딩: 300건/월 × 300 tokens = 90K tokens
- 쿼리 임베딩: 1,000건/월 × 20 tokens = 20K tokens
- 총: 360K tokens/월

월간 비용:
- 360K × $0.00001/1K = $0.0036/월 (거의 무료)
```

### 버전별 전략

| 버전 | 임베딩 모델 | 근거 |
|------|------------|------|
| **V1-V2** | Gemini Embedding API | 빠른 프로토타이핑, 비용 효율 |
| **V3+** | Gemini Embedding API | 비용이 워낙 저렴해서 유지 |

### 중요 원칙: 임베딩 모델 통일

```
⚠️ 임베딩 모델은 반드시 하나만 사용

이유:
1. 벡터 공간 일관성 유지
2. 서로 다른 모델의 임베딩은 비교 불가
3. 모델 변경 시 전체 VectorDB 재구축 필요

현재 선택: Gemini Embedding만 사용
```

## 6. 구현 참조

### 코드 파일
- `3.model/app/services/vectordb_service.py` - 임베딩 생성 및 저장

### 사용 예시

```python
from google import genai

client = genai.Client()

def get_embedding(text: str, task_type: str = "retrieval_document") -> list[float]:
    """텍스트를 768차원 벡터로 변환"""
    result = client.models.embed_content(
        model="gemini-embedding-001",
        contents=text,
        config={"task_type": task_type}
    )
    return result.embeddings[0].values

# 이력서 임베딩 (문서)
resume_embedding = get_embedding("3년 경력 백엔드 개발자...", "retrieval_document")

# 쿼리 임베딩 (검색)
query_embedding = get_embedding("이력서 분석해줘", "retrieval_query")

# VectorDB에 저장
vectordb.add_document(
    collection="resumes",
    id="resume_001",
    embedding=resume_embedding,
    metadata={"user_id": "user_123"}
)
```

### VectorDB 컬렉션 구조

| 컬렉션 | 용도 | 메타데이터 |
|--------|------|-----------|
| **resumes** | 이력서 | user_id, created_at, file_id |
| **job_postings** | 채용공고 | user_id, created_at, file_id |
| **portfolios** | 포트폴리오 | user_id, created_at, file_id |
| **interview_qa** | 면접 Q&A (RAG용) | category, difficulty |
